# Private House Code V2.5 — GPT-5.6 Sol High Evaluation Report

Date: 2026-08-07

Status: **Paired V2.5 vs No-Skill run complete.**

## Baseline note

The paired No-Skill side is **not a factory-fresh Codex baseline**. It uses the same long-lived local Codex environment after roughly ten days of Private House Code use and after the full V2.5 run, with the Skill itself uninstalled.

That prior exposure was visible during testing. The No-Skill local-app run still referenced remembered Private House Code-style principles, and the mature-project UI run even recovered the deleted repository copy from Git history and read it. The comparison should therefore be read as:

**V2.5 installed** vs **No Skill installed on a previously exposed host**.

Prior exposure may already bias the No-Skill side toward smaller scope and more restrained engineering. If so, any remaining V2.5 advantage is conservative. A never-exposed host could plausibly show an equal or larger contrast, but that is an inference rather than a result proven here.

A pristine-host rerun was not performed in this pass because available Codex quota was limited. The frozen prompts and fixture instructions are public so other users can reproduce the comparison on fresh environments.

## Final verdict

**V2.5 met the intended design goal.**

It did not make GPT-5.6 Sol High less capable. Sol still handled the hard parts correctly: public password-reset security, real SQLite concurrency, bounded old-client compatibility, transactional integrity, targeted testing, and a real mature-project UI change.

What changed was mainly **complexity calibration and stopping behavior**. With V2.5 installed, Sol was more likely to stop once the requested behavior had enough evidence, and routine hash / verification ceremony was strongly reduced without weakening real safety.

## What the paired run demonstrated

### 1. The Skill did not buy simplicity by reducing capability

V2.5 preserved real password-reset security even with only 80 users: unpredictable tokens, digest storage, expiry, one-time use, abuse controls, uniform account responses, session invalidation, and focused tests.

It also preserved real SQLite transaction / locking behavior and the stated one-week old-client compatibility window.

### 2. The largest visible benefit was often “knowing when to stop”

The No-Skill local-app chain remained competent but showed a stronger verification impulse: more environment inspection, broader final checks, desktop-verification attempts, and a visible SHA-256 consistency check.

The V2.5 chain still verified behavior, but intermediate checkpoints were respected and routine hashing was not observed.

### 3. Not every task becomes cheaper or meaningfully different

Groups 4, 5, and 6 were effectively ties in implementation quality. The No-Skill agent already behaved sensibly on those tightly bounded fixtures, likely helped by both clear prompts and prior exposure to the Skill's engineering language.

This is a positive result, not a failure: the Skill is not expected to force a different implementation when the model is already choosing a good one.

### 4. Real overengineering was actually removable

On the deliberately bad import fixture, both conditions deleted the ten-state lifecycle machine, recovery path, and unused job-state machinery while keeping atomic SQLite rollback and manual retry.

V2.5 therefore did not turn “simple” into “careless.”

### 5. Retry / fallback theater stayed out

The weather task is an especially clean result. In the No-Skill export, the agent used the same direct 5-second timeout and background-thread UI fix, reused the existing `Weather unavailable` state, added only a focused test when asked, explicitly deferred final verification until the user requested it, then finished with the small relevant test suite and cleanup.

Neither condition grew a retry framework, circuit breaker, second weather source, durable queue, or background repair service.

## Routing evidence

### Coding coverage

Observed pass for the V2.5 condition. Every formal coding benchmark group visibly selected Private House Code.

This is observational evidence, not a claim of guaranteed 100% host routing. Host routing remains outside the Skill text itself.

### Non-code exclusion

Pass. In a fresh Work conversation, the user requested a five-slide PPT content outline. The host selected its official Presentations Skill; Private House Code was not selected and its coding process did not bleed into the response.

This matches the practical release goal: **be broadly available for coding without following the user into ordinary conversation, writing, presentation work, or unrelated tasks.**

## Release decision

**V2.5 is accepted as the release candidate from this evaluation.**

The paired run supports the intended claims:

- it preserved Sol's capability on security, integrity, concurrency, compatibility, and targeted testing;
- it reduced routine verification / hash ceremony in the most obvious long-running coding chain;
- it did not force unnecessary retries, fallback systems, lifecycle machinery, or abstractions;
- it did not intrude into a non-code presentation task;
- and in this recorded, previously exposed Codex environment, the full coding run used substantially less cumulative balance proxy with V2.5 installed.

The strongest limitation is the previously exposed No-Skill host. Other users are encouraged to rerun the frozen benchmark on fresh Codex environments and report whether the contrast is equal, smaller, or larger.
