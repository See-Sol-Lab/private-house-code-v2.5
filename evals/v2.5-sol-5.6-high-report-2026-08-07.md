# Private House Code V2.5 — GPT-5.6 Sol High Evaluation Report

Date: 2026-08-07

Status: **V2.5 side complete and frozen; No-Skill comparison pending.**

## Baseline note

The paired No-Skill side is **not a factory-fresh Codex baseline**. It uses the same long-lived local Codex environment after roughly ten days of Private House Code use and after the full V2.5 run, with the Skill itself uninstalled. That prior exposure is visible in practice: the first No-Skill local-app run still referenced remembered Private House Code-style principles, and the mature-project UI run even recovered the deleted repository copy from Git history and read it. The comparison should therefore be read as **V2.5 installed vs No Skill installed on a previously exposed host**. Prior exposure may already bias the No-Skill side toward smaller scope and more restrained engineering, so any remaining V2.5 advantage may be conservative; a never-exposed host could plausibly show an equal or larger contrast, but that is an inference rather than a result proven here. A pristine-host rerun was not performed in this pass because available Codex quota was limited; the frozen prompts and fixture instructions are public specifically so other users can reproduce the comparison on fresh environments.

## Judge verdict

**V2.5 passed the full evaluated side of the benchmark.**

- Coding groups passed: **6 / 6**
- Coding score: **58 / 60**
- Non-code routing sanity check: **Pass**
- User repair turns required by delivered features: **0**
- Routine per-turn hash ritual observed: **No**
- Real security, data integrity, concurrency, and bounded compatibility preserved: **Yes**
- Unpaid lifecycle/retry/fallback machinery removed or avoided when it had no current job: **Yes**
- Observable capability regression from using the Skill: **None in this run**

The most important result is that the Skill did **not** make GPT-5.6 Sol High less capable. Sol still handled the hard parts correctly: public password-reset security, real SQLite concurrency, bounded old-client compatibility, transactional integrity, targeted testing, and a real mature-project UI change. The Skill changed complexity and stopping behavior rather than flattening the model's reasoning ability.

The V2.5 condition therefore met the intended design target: **keep Sol smart, but stop ordinary coding work from turning into a bank, a resilience platform, or an endless verification loop.**

## What the run demonstrated

- **No "simplify by becoming careless" failure.** Password-reset security stayed intact even for only 80 users.
- **No "simplify by deleting real concurrency" failure.** SQLite transaction/locking behavior and the stated compatibility window were preserved.
- **Real overengineering was actually deleted.** The deliberately bad ten-state import lifecycle was reduced to the real user path while keeping rollback and manual retry.
- **Retry/fallback theater stayed out.** The weather fix used a direct timeout, moved the blocking call off the UI thread, reused the existing unavailable state, and did not grow a retry framework, circuit breaker, second API, durable queue, or repair worker.
- **Intermediate checkpoints worked.** When the user reserved final verification for the next turn, Sol stopped instead of repeatedly doing a full verification cycle.
- **Routine hashing was not observed across the formal V2.5 coding run.**
- **Routing stayed scoped.** Formal coding tasks visibly selected Private House Code; a fresh PPT-content task selected the host's Presentations Skill instead and did not select Private House Code.

A short visible indication that Private House Code was selected is treated as useful routing observability, not as ceremony. Only unnecessary recitation of methodology or repeated process explanation counts as overhead.

## Routing evidence

### Coding coverage

Observed pass. Every formal coding benchmark group in this V2.5 run selected Private House Code.

This is observational evidence, not a claim of guaranteed 100% host routing. Host routing is outside the Skill text itself.

### Non-code exclusion

Pass. In a fresh Work conversation, the user asked for a five-slide PPT content outline. The host selected its official Presentations Skill. Private House Code was not selected, and its coding process did not bleed into the response.

This matches the practical release goal: **be broadly available for coding without following the user into ordinary conversation, writing, presentation work, or unrelated tasks.**
